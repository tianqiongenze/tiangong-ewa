## 1. 为什么先做这个（Why）

搬运是工厂里**付费意愿最明确、成功率要求最可量化**的场景：
- 雅迪基地物料流密集（电池包/车架/包材），两班制人工成本清晰（docs/01 §5）
- 结构化程度高，VLA 成功率可达标（对标 3C 上下料 100% 案例）
- 零写操作风险之外的物理风险已被红线覆盖（安全区 + 人工令牌）

**本 spec 就是那个最小闭环**：它同时验证 Harness 全组件（分解/审批/调度/安全/证据/降级/飞轮）。

## 3. 功能需求（EARS）

| ID | 需求 |
|---|---|
| FR-001-01 | [Event] 当用户提交 TRANSPORT 作业单时，系统应分解为 PICK → TRANSPORT → PLACE 三任务 DAG。 |
| FR-001-02 | [State] 当作业单参数含 weight_kg 时，系统应将其传播到全部搬运动作（安全与匹配依据）。 |
| FR-001-03 | [State] 当作业单参数含目标坐标 (x, y) 时，系统应将其挂到末位任务（安全审查对象）。 |
| FR-001-04 | [Event] 当三要素（物料/起点/终点）缺失时，系统应拒单并说明缺什么。 |
| FR-001-05 | [Ubiquitous] 系统应在任务完成时挂载证据：trace + telemetry + skill_version。 |
| FR-001-06 | [Unwanted] 若证据不完整，系统不得将任务标记 DONE（应打回重做）。 |
| FR-001-07 | [Event] 当任务失败时，系统应按降级阶梯处置（L1→L2→L3→L4）并显式标记 degraded。 |
| FR-001-08 | [Event] 当任务完成时，系统应记录 episode（含 consent_id）。 |
