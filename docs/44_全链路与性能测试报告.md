## 3. 数据层：1 亿条怎么建模

### 3.1 为什么单独建分析库

业务库（作业单/任务/技能/审计）必须小而快——它承载状态机与不变量，写路径要低延迟。
1 亿条**作业事实**（谁在什么时候、用哪个技能、干了多久、成没成）属于典型的分析型负载，
单独落在只读分析库，与业务库物理隔离：

```
业务库 tiangong.db（MB 级）        分析库 tiangong_bulk.db（5 GiB）
├── work_orders  ← 状态机           ├── wo_fact      15,000,000
├── tasks        ← 九态迁移          ├── task_fact    40,000,000
├── episodes     ← 证据与飞轮         ├── episode_fact 35,000,000
├── skills       ← 四态治理          ├── audit_fact   10,000,000
├── audit_log                       └── agg_*（预聚合读模型）
└── zones
```

### 3.2 表结构与体积

| 表 | 行数 | 含义 | 索引 |
|---|---|---|---|
| `wo_fact` | 15,000,000 | 作业单事实（站点/类型/状态/时长/成功） | `created_ts`、`(site, created_ts)` |
| `task_fact` | 40,000,000 | 任务事实（类型/机器人/技能/重试） | `order_id`、`start_ts` |
| `episode_fact` | 35,000,000 | 技能执行事实（成功/时长） | `ts`、`(skill, ts)` |
| `audit_fact` | 10,000,000 | 审计动作（审批/停机/红线拦截） | `ts` |
| **合计** | **100,000,000** | — | 7 个索引 |

**紧凑设计**：全部字段为 INTEGER 编码（kind/status/skill 用整数码，语义在 `analytics.py` 还原），
单行 25–40 字节——这是 1 亿条能压进 5 GiB 的原因。若用 TEXT 主键 + JSON 参数，同样数据量会膨胀 3–5 倍。

### 3.3 装载实测

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 生成 + 写入 1 亿条 | **1,027 s**（约 9.7 万行/s） | 每批 10 万行 `executemany`，`journal_mode=OFF`、`synchronous=OFF` |
| 建 7 个索引 | **357 s** | 装载后建索引（比边写边维护快得多） |
| 落盘体积 | **5.03 GiB** | 含索引与 WAL |

> 纪律：装载期关闭日志是为了速度，**仅在离线灌数时允许**；装载完成后立即切回 WAL（脚本自动执行）。

## 4. 查询路径：一次"慢查询"引出的架构修正

### 4.1 问题：索引不等于快

第一版 `analytics.py` 直接对明细表做时间窗聚合（`WHERE created_ts >= ?`）。
按常识这应该走 `idx_wo_ts`，实测结果却是：

| 查询 | 耗时（1 亿条明细，走索引） |
|---|---|
| 近 1 天概览 | **61.6 s** |
| 近 7 天概览 | **173.5 s** |
| `COUNT(*)`（scale） | 2.16 s |

**根因**：二级索引只存 `(created_ts, rowid)`。7 天窗口命中 116 万行，
每行都要按 rowid **回表**取 `status/kind/duration_ms`——116 万次随机读，
在 5 GiB 文件上就是典型的海量随机 I/O。**索引把"全表顺序扫描"换成了"百万次随机读"，反而更慢。**

### 4.2 解法：预聚合读模型（rollup）

聚合口径是固定的（按天/小时/类型/技能/动作），完全可以离线算好——
这就是数仓的物化视图/宽表思路：**把随机 I/O 换成一次顺序扫描**。

| 预聚合表 | 行数 | 口径 |
|---|---|---|
| `agg_daily` | 1,365 | 天 × 基地 × 类型：单量/完成/失败/中止/时长和 |
| `agg_daily_task` | 91 | 天：任务数、重试数（任务表无 site 维度，按天单行避免重复计数） |
| `agg_daily_skill` | 728 | 天 × 技能：episode 数/成功数/时长和 + **6 档时长分桶**（用于 p95 估算） |
| `agg_daily_action` | 910 | 天 × 审计动作 |
| `agg_hourly` | 2,161 | 小时：作业单吞吐 |

构建耗时 **3 分 13 秒**（一次全表扫描 + 分组，无随机回表）：

| 步骤 | 耗时 |
|---|---|
| `agg_daily` | 26.96 s |
| `agg_daily_task` | 67.99 s |
| `agg_daily_skill` | 76.04 s |
| `agg_daily_action` | 14.99 s |
| `agg_hourly` | 5.18 s |

### 4.3 效果对比

| 查询 | 明细扫描（索引） | 预聚合 | 提升 |
|---|---|---|---|
| 近 1 天概览 | 61,641 ms | **0.30 ms** | 205,470× |
| 近 7 天概览 | 173,537 ms | **0.23 ms** | 754,509× |
| 近 30 天概览 | —（预计 > 600 s） | **0.46 ms** | — |
| 近 90 天（全量） | — | **1.06 ms** | — |
| 小时吞吐 | — | **0.05 ms** | — |
| 审计分布 7 天 | — | **0.06 ms** | — |
| 单作业单时间线（点查） | — | **3.26 ms** | 明细点查本就该快 |
| 数据规模 `COUNT(*)` | 2,160 ms | 2,646 ms | 保持明细（缓存 30 s） |

> 说明：`summary` 响应里带 `"source": "rollup" | "raw"`，无预聚合的小库（测试/E2E）自动回退明细扫描，
> 保证同一份代码在 20 万行与 1 亿行两种规模下都正确。

### 4.4 p95 的口径（诚实标注）

预聚合表不保留原始分布，p95 由**时长分桶累计**估算：
`<1s / 1–5s / 5–30s / 30–60s / 60–120s / ≥120s`，取累计到 95% 的桶上界。
响应中标注 `"p95_basis": "bucket_estimate"`。
合成数据的时长是均匀分布（0.5–240 s），因此 p95 落在 `≥120s` 桶，返回 240,000 ms——
这是**口径**而非缺陷；真实产线数据分布集中，分桶精度更高（可按需细化为 12 档）。

## 5. 缓存层：Redis 预热与命中

### 5.1 实现

| 项 | 设计 |
|---|---|
| L1 | 进程内 TTL 字典，命中路径无 I/O |
| L2 | `RedisL2`（redis-py），JSON 序列化，前缀 `tg:`，SCAN 前缀失效（不用 KEYS） |
| 降级 | L2 任何异常被吞掉 → 只用 L1，功能不受影响（宪法第四条降级纪律） |
| 观测 | `hits / misses / l1_hits / l2_hits / hit_rate / l2_available` 暴露于 `/observability/metrics` |
| 安全 | **红线判定与人工令牌永不进缓存**（缓存会引入时序漏洞） |

### 5.2 预热

```bash
python tools/redis_compat.py                 # 起 Redis 兼容服务
python tools/warmup_cache.py --bulk-db data/tiangong_bulk.db --days 1,7,30,90 --timelines 200
```

| 项 | 结果 |
|---|---|
| 写入 key | **211**（scale 1 + summary 4 + hourly 2 + audit 4 + timeline 200） |
| 体积 | **138.6 KiB** |
| 耗时 | **1.01 s** |
| TTL | 600 s + 0–60 s 随机抖动（避免同时过期造成雪崩） |
| 校验 | `tg:an:scale` / `tg:an:summary:7` / `tg:an:timeline:15000000` 均命中，TTL 607/614/610 s |

### 5.3 预热效果（冷进程首请求）

| 场景 | 延迟 |
|---|---|
| 进程刚启动，首个 `summary?days=7`（L2 命中） | **19.6 ms** |
| 第二次（L1 命中） | **2.5 ms** |
| 第三次（L1 命中） | **1.9 ms** |
| 未预热的 `summary?days=60`（rollup 计算 + 回填） | **4.7 ms** |

### 5.4 压测期缓存表现

| 指标 | 值 |
|---|---|
| 命中 | 5,232 |
| 未命中 | 2 |
| **命中率** | **99.96%** |
| L1 / L2 命中 | 5,194 / 38 |

### 5.5 过程中发现并修复的缺陷（重要）

**缺陷**：`MultiLevelCache.get()` 在 L2 命中后调用 `self.set(key, v)` 回填 L1，
而 `set()` 会用默认 TTL（5 s）**同时重写 L2**——于是"预热 600 s 的键"被一次读操作
降级成 5 s，随后集体过期，预热形同虚设。

**现象**：预热完成后立刻查询，`tg:an:scale`、`tg:an:summary:7` 的 TTL 变成 -2（已过期），
而未被读取的 `tg:an:summary:30` 仍为 600 s。

**修复**：新增 `_set_l1()`，L2 命中只回填 L1，**不改写 L2 的 TTL**；并补回归测试
`test_l2_hit_does_not_shorten_l2_ttl`（断言 L2 TTL 仍 > 500 s）。

> 这类缺陷只在"预热 + 长 TTL"组合下暴露，单测不覆盖就一定会漏。已在 docs/08 记录为测试用例。

## 8. 瓶颈分析与调优记录

| # | 现象 | 根因 | 处置 | 效果 |
|---|---|---|---|---|
| 1 | 7 天聚合 173 s | 二级索引回表 → 百万次随机读 | 预聚合读模型 | 0.23 ms |
| 2 | 预热键几分钟后失效 | L2 命中回填 L1 时连带重写 L2 短 TTL | 拆分 `_set_l1`，不改 L2 TTL | 命中率 99.96% |
| 3 | `COUNT(*)` 2.6 s | 1 亿行全表计数 | 缓存 30 s + 只在看板展示 | 可接受 |
| 4 | 任务数聚合虚高 15 倍 | 任务表无 site 维度，按 (day,site,kind) 存重复计数 | 独立 `agg_daily_task` 按天单行 | 口径正确 |
| 5 | 冷启动首屏 19.6 ms | 进程内 L1 为空 | Redis 预热 + L2 | 次请求 1.9 ms |
| 6 | 单进程写库 | SQLite 单写者 | 压测单实例；扩展路径见 docs/09（PostgreSQL） | 写 P95 2.66 ms |

**已知边界（不粉饰）**：

1. SQLite 单写者：写吞吐上限受限于单连接串行写；生产规模化需 PostgreSQL（A7/A9 决策）。
2. 单进程 Python：GIL 下 CPU 密集查询会互相影响；本次压测读路径几乎全命中缓存，未触顶。
3. `fakeredis` 非生产级：单机内存实现，无持久化/集群；仅用于链路验证。
4. 合成数据分布均匀：真实产线时长/成功率分布更集中，p95 分桶估算会更准。
5. 压测在本机（与压测工具同机），存在资源竞争；数值偏保守。

## 9. 复现步骤

```bash
# 0. 依赖（项目根目录）
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r impl/services/agent-runtime/requirements.txt
.venv/Scripts/python.exe -m pip install redis fakeredis locust playwright

# 1. 生成 1 亿条分析库（约 17 分钟 + 建索引 6 分钟）
python tools/gen_bulk_data.py --rows 100000000 --db data/tiangong_bulk.db --force

# 2. 构建预聚合读模型（约 3 分钟）
python tools/build_rollup.py --db data/tiangong_bulk.db --rebuild

# 3. 起缓存并预热
python tools/redis_compat.py &
python tools/warmup_cache.py --bulk-db data/tiangong_bulk.db --days 1,7,30,90 --timelines 200

# 4. 起压测服务（文件库 + 分析库 + Redis L2）
cd impl/services/agent-runtime
TIANGONG_DB=../../data/tiangong.db \
TIANGONG_BULK_DB=../../data/tiangong_bulk.db \
TIANGONG_REDIS_URL=redis://127.0.0.1:6379/0 \
PYTHONPATH="../../packages/tiangong_core;." \
../../../.venv/Scripts/python.exe -m granian --interface asgi app.server:app --port 8200

# 5. 功能测试
cd impl && make test && make e2e

# 6. 压测
make perf-k6
make perf-locust
```
