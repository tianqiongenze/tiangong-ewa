## 2. 具身智能体分层：大脑 / 小脑 / 脊髓

借鉴 2026 年 VLA 三代演进共识（端到端 VLA → 增强型 VLA → 类脑 VLA，如 NeuroVLA 的
大脑-小脑-脊髓架构），本项目的工程映射：

| 层 | 职责 | 本项目实现 | 时延要求 |
|---|---|---|---|
| **大脑**（认知） | 意图理解、任务分解、调度决策、异常处置 | agent-runtime（LLM 规划器 + 规则兜底） | 秒级 |
| **小脑**（技能） | 具体动作技能执行（取放/搬运/读数） | 具身技能（VLA 或规则，受治理） | 百毫秒 |
| **脊髓**（反射） | 围栏、停机、急停 | tiangong_core.safety（运行时层） | **毫秒级** |

> 关键架构决策：**脊髓层不依赖大脑**。即使 LLM 挂了，围栏/停机/急停依然生效
> （对应 VLA 类脑架构的"碰撞反射 20ms"思想，用确定性代码实现）。

## 3. C4-L2 容器图

| 容器 | 技术 | 职责 |
|---|---|---|
| agent-runtime | Python / Litestar / Granian | REST + MCP + A2A + 编排闭环 |
| tiangong_core | 纯 Python 包 | 领域核（分解/调度/安全/证据/技能/飞轮） |
| repository | SQLite WAL（写主读从双连接） | 作业单/任务/episode/技能/审计/安全区持久化（CQRS 读写分离） |
| multi-level cache | L1 进程内 TTL + L2 可插拔（Redis 接口预留） | 热点读加速、前缀失效、命中率统计 |
| event bus | Event + Transport 抽象（Memory 实现；Pulsar/Redis 预留） | 领域事件发布/重放/统计 |

## 4. 领域模型（核心对象）

```
WorkOrder ── decompose ──▶ TaskGraph ── schedule ──▶ Task ── execute ──▶ Evidence
   │                            │                        │                  │
   │ kind/params                │ DAG                     │ 九态              │ trace/遥测/版本
   ▼                            ▼                        ▼                  ▼
 五类作业单              拓扑序/就绪集            状态机白名单          verify_evidence
                                                    │
                       Robot ── match ──▶ Candidate（可解释打分）
                       Skill ── 四态 ──▶ 生效版本
                       SafetyZone ── 围栏 ──▶ Verdict
```

关键不变量：

1. `TaskGraph` 必须无环（构造时 Kahn 校验）
2. 任务状态只能沿白名单迁移（`lifecycle.py`）
3. `Evidence` 只追加不修改（`replace` 语义）
4. 技能只能引用 APPROVED 版本

## 5. 运行时基础设施（v1.1 新增）

v1.0 的架构分层干净但缺少工程化支撑（无缓存、无读写分离、无事件、无链路追踪），
与 Diting-PdM 已具备的能力相比是退步。v1.1 按 docs/43 §4 补齐五项，全部在 `app` 层装配、
核心包零改动（守住宪法第九条）。

### 5.1 CQRS 读写分离（`app/repository.py`）

| 项 | 设计 |
|---|---|
| 写侧 | 主连接，串行写事务；WAL 模式下不阻塞读 |
| 读侧 | 从连接（只读），承担看板/查询/统计 |
| 一致性 | 写后强一致场景（审批后立即执行）强制走主连接 |
| 表 | `work_orders` / `tasks` / `episodes` / `skills` / `audit_log` / `zones` |
| 迁移 | 内建 `CREATE TABLE IF NOT EXISTS`，零外部依赖；生产可平滑换 PostgreSQL |
| 测试隔离 | `file:tiangong_<uuid>?mode=memory&cache=shared`（多连接共享内存库） |

> CQRS 在本项目的首要价值不是性能，而是**语义清晰**：写模型承载状态机与不变量，
> 读模型服务看板与审计，两者演进解耦。

### 5.2 多级缓存（`app/cache.py`）

- **L1**：进程内 TTL 字典（默认短 TTL，按数据热度分层）
- **L2**：可插拔接口（Redis 预留）；L2 故障自动降级为仅 L1，**不影响功能**
- **失效**：支持前缀批量失效（技能审批/安全区变更时使用）
- **观测**：`hits / misses / hit_rate` 暴露于 `/observability/metrics`
- **纪律**：缓存只缓存**读模型**，绝不缓存红线判定与令牌（安全判定必须实时）

### 5.3 事件总线（`app/events.py`）

- `Event`（frozen dataclass）+ `Transport` Protocol + `MemoryTransport`（生产换 Pulsar/Redis）
- 事件类型覆盖：作业单提交/审批/任务状态迁移/降级/停机/技能变更/证据落库
- **投递失败不阻塞主链路**（降级纪律）：事件可重放，业务不可重放
- `GET /events` 暴露统计与最近 20 条，供值班排障

### 5.4 可观测（`app/otel.py`）

对齐 OTel GenAI Semantic Conventions，三层结构 **Session > Trace > Span**：

| 层 | 含义 | 本项目取值 |
|---|---|---|
| Session | 一次人机协作会话 | 作业单生命周期 |
| Trace | 一次编排闭环 | `trace_id`（贯穿分解→执行→证据） |
| Span | 单个动作 | `plan.*` / `safety.*` / `skill.*` / `evidence.*` |

语义属性：`gen_ai.system`、`gen_ai.request.model`、`gen_ai.usage.input_tokens`、
`gen_ai.usage.output_tokens`、`gen_ai.response.finish_reasons`。
无 OTel SDK 硬依赖（可零成本接入现有 APM），导出端点 `/observability/spans`。

### 5.5 多品牌适配（`app/robots/vda5050.py` + `AdapterRegistry`）

| 能力 | 说明 |
|---|---|
| VDA 5050 | MQTT 主题规范、`order`/`instantAction` 构造、`state` 解析、dry-run outbox |
| 私有协议 | 实现同一 `RobotLink` 协议即可接入（gRPC 骨架见 `contracts/proto`） |
| 注册表 | 按品牌注册/工厂创建/健康探测，`GET /adapters/health` 统一暴露 |
| 混场纪律 | 适配器只做**协议翻译**，不做业务决策；调度与安全判定在核心层统一 |

### 5.6 智能体互联（`app/a2a.py`）

- `GET /a2a/v1/card`：Agent Card（能力声明）
- `POST /a2a/v1/tasks`：意图委派入口（如 Diting-PdM 的设备异常 → 天工巡检作业单）
- 委派只传**意图与参数**，不传执行权限；落地仍需走本平台的审批与红线

### 5.7 分析库与读模型（1 亿条事实）

业务库保持小而快；**作业事实**（1 亿条）单独落只读分析库，并构建预聚合读模型：

```
业务库 tiangong.db（MB 级，写侧）      分析库 tiangong_bulk.db（5 GiB，读侧）
├── work_orders  ← 状态机不变量         ├── wo_fact / task_fact / episode_fact / audit_fact
├── tasks        ← 九态迁移              └── agg_daily / agg_daily_task / agg_daily_skill
├── episodes     ← 证据与飞轮                  / agg_daily_action / agg_hourly
├── skills / audit_log / zones
```

| 层 | 职责 | 时延（实测） |
|---|---|---|
| 明细表 | 点查（单作业单时间线） | 3.26 ms |
| 预聚合表 | 时间窗聚合（1/7/30/90 天） | 0.23–1.06 ms |
| 多级缓存 | 首屏热 key（预热 + L1/L2） | 1.9 ms（L1）/ 19.6 ms（L2 首击） |

**为什么必须预聚合**：对 1 亿条按时间窗聚合会退化为百万次随机回表
（实测 7 天 173.5 s）；预聚合把随机 I/O 换成一次顺序扫描，在线只读几千行。
无预聚合的小库自动回退明细扫描（`summary.source = raw|rollup`），保证两种规模同一份代码。

（完整实测与调优记录见 docs/44）

## 6. 关键架构决策（ADR 索引）

| # | 决策 | 理由 | 详址 |
|---|---|---|---|
| A1 | 软硬分层、契约先行 | 本体过剩、软件稀缺；协议差异关 adapter | contracts/proto |
| A2 | 大脑/小脑/脊髓三层 | 安全不依赖 LLM 可用性 | §2 |
| A3 | 规则规划器为默认兜底 | 可解释、可单测、LLM 挂了能跑 | docs/05 |
| A4 | 证据链作为完成判据 | 无证据不 DONE（可审计） | FR-502 |
| A5 | 技能四态 + 灰度 + 回滚 | 受控资产（宪法第十条） | FR-601–603 |
| A6 | episode 强制 consent_id | 数据合规（不出厂区） | FR-702 |
| A7 | SQLite 优先（演示）/ PostgreSQL（生产） | 与 Diting-PdM 双后端同构 | docs/09 |
| A8 | 单基地双副本起步 | 可用性目标 99.5% | NFR-107 |
| A9 | CQRS 读写分离（写主/读从） | 语义清晰优先，性能次之；为 PostgreSQL 铺路 | §5.1 |
| A10 | 多级缓存只缓存读模型 | 红线与令牌必须实时，缓存会引入安全风险 | §5.2 |
| A11 | 事件总线不阻塞主链路 | 事件可重放、业务不可重放 | §5.3 |
| A12 | 自研轻量 tracer 对齐 OTel SemConv | 避免 SDK 强绑定；可零成本接入现有 APM | §5.4 |
| A13 | 适配器只翻译协议 | 业务决策统一在核心层，防止混场语义漂移 | §5.5 |
| A14 | 分析库与业务库物理分离 | 1 亿条事实与状态机写路径的资源特征完全不同 | §5.7 |
| A15 | 聚合走预聚合读模型，不直接扫明细 | 索引回表会把聚合退化为百万次随机读（实测 173 s → 0.23 ms） | §5.7 / docs/44 |
| A16 | 缓存 L2 命中只回填 L1，不改写 L2 TTL | 否则预热的长 TTL 被一次读操作降级为短 TTL（实测缺陷） | §5.2 |

## 7. 部署视图

- **演示/CI**：单进程 Litestar + MockRobotDriver（无硬件），`TIANGONG_DB` 默认内存库
- **基地边缘**：K3s 双副本 agent-runtime + 本地 SQLite（`TIANGONG_DB=/data/tiangong.db`，WAL）+ 本地 episode 缓存（弱网可断点续传）
- **总部中心**：汇聚各基地脱敏 episode + 技能注册中心 + 看板

（清单见 `impl/deploy/k8s/`，多基地拓扑详 docs/09 §4，运维细则详 docs/38）

## 8. 质量属性场景

| 属性 | 场景 | 响应 |
|---|---|---|
| 可用性 | LLM 规划器超时 | 降级规则规划器（FR-105） |
| 可用性 | 机器人执行失败 | 降级阶梯 L1→L4（FR-504） |
| 可用性 | L2 缓存不可用 | 自动退化为仅 L1，功能不受影响（§5.2） |
| 安全性 | 停止区有人 | 毫秒级停机（FR-403） |
| 安全性 | 缓存与安全判定冲突 | 红线/令牌**不进缓存**，永远实时（A10） |
| 可审计 | 事故复盘 | trace_id 重建全链 + 审计日志（FR-503） |
| 可修改性 | 换机器人厂商 | 新 adapter，核心不动（A1/A13） |
| 可扩展 | 新增品牌混场 | 注册表加一条 + 健康探测（§5.5） |
| 性能 | 高峰 20 作业单并发 | 读走缓存与从库，目标 NFR-101/102 |
| 性能 | 看板高频查询 | 多级缓存 + 读连接，不打写侧 |
