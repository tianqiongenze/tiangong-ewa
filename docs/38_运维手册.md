## 2. SLO / SLA

### 2.1 服务等级目标（内部 SLO）

| 指标 | 目标 | 测量口径 | 告警阈值 |
|---|---|---|---|
| 平台可用性 | ≥ 99.5%（月度） | `/healthz` 1 分钟探测成功率 | 连续 3 次失败 |
| 作业单受理 P95 | ≤ 800 ms | `POST /work-orders` 服务端耗时 | P95 > 1.5 s 持续 10 min |
| 编排闭环 P95 | ≤ 5 s（不含机器人物理动作） | `run` 端点到返回 | P95 > 8 s 持续 10 min |
| 安全审查耗时 P99 | ≤ 50 ms | `safety.review` span | P99 > 100 ms |
| 急停生效 | ≤ 100 ms（软件侧）/ ≤ 20 ms（脊髓层硬件反射） | 急停端点到驱动停止 | 任一次 > 200 ms 即事故 |
| 证据完整率 | 100% | DONE 任务中证据三类齐全占比 | 任一缺失即 S1 |
| 数据零丢失 | RPO ≤ 5 min | WAL 备份间隔 | 备份失败 1 次即告警 |

### 2.2 对外服务承诺（SLA，招标服务分项）

| 事件等级 | 定义 | 响应时限 | 恢复时限 | 现场到场 |
|---|---|---|---|---|
| P1 安全/停产 | 红线失效、停机失灵、整线停产 | **15 min** | 4 h | 同城 4 h / 异地 24 h |
| P2 主链路中断 | 作业单无法受理或无法执行 | 30 min | 8 h | 24 h |
| P3 功能降级 | 单品牌适配失效、看板不可用 | 2 h | 3 个工作日 | 按需 |
| P4 一般问题 | 文案、统计口径、体验 | 1 个工作日 | 下个迭代 | 远程 |
| 咨询 | 使用与配置 | 4 h | — | 远程 |

> 计时起点：工单进入值班台并完成首次响应确认。P1 事件每 30 min 向客户同步一次进展。

## 3. 值班与响应体系

### 3.1 三级值班

| 层级 | 角色 | 职责 | 值守方式 |
|---|---|---|---|
| L1 | 值班工程师 | 看板巡检、告警确认、按 Runbook 处置 P3/P4、P1/P2 首响 | 7×24 轮班 |
| L2 | 平台运维 | 服务重启/扩缩容、数据库与缓存、适配器联调、变更执行 | 7×24 待命（30 min 到场） |
| L3 | 研发值守 | 代码级缺陷、红线逻辑、协议栈问题、紧急补丁 | 7×24 电话待命 |

### 3.2 升级路径

```
告警/来电 ──▶ L1 确认（5 min 内）
                │ 判级
                ├─ P4/P3 ──▶ L1 自行处置（Runbook §7）
                ├─ P2 ────▶ L1 + L2 联合，30 min 未定位即升级 L3
                └─ P1 ────▶ 立即：① 停机 ② 通知安全专员与客户接口人
                              ③ 拉起 L2+L3 ④ 启动事故复盘（24 h 内出报告）
```

### 3.3 交接班（每班必做）

1. 未闭环告警逐条口述 + 书面留痕（工单号/现象/已采取措施）
2. 本班发生的所有 **急停/停机/红线拦截** 事件必须交接（不得只写"已恢复"）
3. 变更窗口内的发布与回滚记录
4. 下一班需重点盯的机器人（电量低、故障率高、待校准）

## 4. 日常巡检

### 4.1 一条命令巡检

```bash
cd impl
make smoke            # healthz + robots
curl -s localhost:8000/tg-api/v1/observability/metrics | python -m json.tool
curl -s localhost:8000/tg-api/v1/adapters/health  | python -m json.tool
curl -s localhost:8000/tg-api/v1/events           | python -m json.tool
```

### 4.2 五分钟巡检清单

| # | 检查项 | 命令/位置 | 正常判据 | 异常动作 |
|---|---|---|---|---|
| 1 | 进程存活 | `curl -s localhost:8000/healthz` | `status=ok` | 重启 + 查日志 |
| 2 | 副本数 | `kubectl get pods -n tiangong` | 2/2 Running | 查 OOM/探针 |
| 3 | 机群在线 | `GET /robots` | 在线数 = 台账数 | 查适配器健康 |
| 4 | 低电量机 | `GET /robots` 中 `battery<20` | 0 台（或已排充电） | 调度排除 + 派充电任务 |
| 5 | 适配器 | `GET /adapters/health` | 全部 `ok=true` | 查 broker / 网关 |
| 6 | 事件总线 | `GET /events` | `failed=0`，无积压 | 查 transport / 消费端 |
| 7 | 链路错误 | `GET /observability/metrics` | `spans_error=0` | 按 trace_id 拉 span |
| 8 | 缓存命中 | 同上 `cache.hit_rate` | ≥ 0.6（稳态） | 查 TTL 配置与失效风暴 |
| 9 | 审计留痕 | `GET /audit?limit=20` | 有当日审批/急停记录 | 审计断流即 S1 隐患 |
| 10 | 磁盘 | `df -h /data` | 使用率 < 75% | 清理 episode 分片/归档 |
| 11 | 数据库 | `sqlite3 $TIANGONG_DB "PRAGMA integrity_check;"` | `ok` | 立即备份 + 切只读 |
| 12 | 看板 | 打开 `web/index.html` | KPI/地图/任务板有数 | 查数据接口与 CORS |

### 4.3 看板与接口一致性核对

看板是**只读投影**，出现"看板有、接口无"或反之，按以下顺序排查：

1. 看板数据源指向的环境是否正确（dev/staging/prod 三套地址易混）
2. `GET /work-orders` 与看板任务板条数是否一致（差 1~2 条属刷新时序）
3. episode 统计是否落后（看板 30 s 轮询，属正常延迟）
4. 若差异持续 > 5 min，判定为数据面故障，升级 L2

### 5.3 链路追踪用法（排障核心手段）

每次作业单执行都带 `trace_id`。排障三步：

```bash
# 1. 取 trace_id（作业单详情里有）
curl -s localhost:8000/tg-api/v1/work-orders/WO-xxxx | python -m json.tool

# 2. 拉该 trace 的全部 span（含安全审查/执行/证据）
curl -s "localhost:8000/tg-api/v1/observability/spans?trace_id=<TRACE>" | python -m json.tool

# 3. 看审计与事件
curl -s "localhost:8000/tg-api/v1/audit?limit=100" | python -m json.tool
curl -s localhost:8000/tg-api/v1/events | python -m json.tool
```

判读要点：

- `span.name` 前缀区分层：`safety.*`（脊髓层）、`skill.*`（小脑）、`plan.*`（大脑）
- `status=ERROR` 的 span 优先看 `attributes` 里的 `error.type` / `gen_ai.*`
- span 断链（有父无子）通常意味着进程重启或异常退出

## 6. 应急响应

### 6.1 安全事件（最高优先级）

**触发**：人员进入停止区、机器人越界、急停、红线拦截、异常接近。

处置顺序（不可调换）：

```
① 停机        看板急停 / POST /robots/{id}/estop
② 隔离        该机器人置 OFFLINE，调度排除；同区其余机器人降速或停
③ 通报        安全专员 + 客户接口人 + L3（10 min 内）
④ 取证        导出 trace_id、span、审计、episode、现场影像（只读，不得修改）
⑤ 复盘        24 h 内出事故报告：时间线 / 根因 / 红线是否生效 / 改进项
⑥ 恢复        人工确认现场安全 + 安全专员签字 → 解除隔离 → 重新审批作业单
```

**红线相关事故的额外要求**：任何"红线未拦截"事件按 **S1 缺陷** 处理，立即停止相关技能版本发布，冻结灰度。

### 6.2 机器人失联

| 步骤 | 动作 | 判据 |
|---|---|---|
| 1 | 查适配器健康 | `GET /adapters/health` 该品牌 `ok=false` |
| 2 | 查网络与 broker | `mosquitto_sub -h <broker> -t 'uagv/v2/*/state' -C 1 -W 3` |
| 3 | 查机器人本体 | 现场确认电源/急停按钮/网络指示灯 |
| 4 | 任务处置 | 该机器人任务转 `FAILED`，走降级阶梯（L2 规则兜底 → L3 遥操） |
| 5 | 恢复 | 重连后先 `health` 再纳入调度；**不得直接恢复执行中的任务**，需重新审批 |

### 6.3 LLM / 规划器故障

- 现象：`plan.*` span 超时或报错，作业单停在 PENDING
- 处置：系统应自动降级到规则规划器（docs/05），验证方式——下单后 `tasks` 非空即为兜底生效
- 若规则规划器也失败：判 P2，L3 介入；**不得手工改数据库造任务**

### 6.4 数据库异常

| 现象 | 处置 |
|---|---|
| `database is locked` | 确认是否长事务；WAL 模式下读不阻塞写，多为备份进程占用 → 错峰 |
| `disk I/O error` | 立即停止写入（服务切只读），备份现有文件，检查磁盘 |
| `integrity_check` 非 ok | **禁止继续写入**；用最近备份恢复；保留损坏文件供分析 |
| 文件被误删 | 从 5 min 前的 WAL 备份恢复（§8），RPO ≤ 5 min |

### 6.5 缓存故障

- L2（外部缓存）不可用：系统自动降级为仅 L1，**功能不受影响**，仅性能下降 → 判 P3
- 缓存击穿/雪崩：临时调大 TTL、开启请求合并；排查是否批量失效（`invalidate_prefix` 被误用）

### 6.6 事件总线积压

- `events.stats.failed > 0` 或积压增长：先看消费者是否存活，再看 transport 连接
- 处置原则：**事件可重放，业务不可重放**——优先保证作业单与证据写入成功，事件补投

## 7. 故障处置 Runbook（症状 → 处置）

| # | 症状 | 可能原因 | 定位 | 处置 |
|---|---|---|---|---|
| 1 | `/healthz` 502 | 进程崩溃 / 探针失败 | `kubectl logs --previous` | 重启；看 OOMKilled |
| 2 | 下单返回 400 | 参数缺 `weight_kg` / 坐标 / 未知 kind | 响应 `detail` 字段 | 按 docs/06 契约补齐参数 |
| 3 | 执行返回 400「未审批」 | 跳过审批直接 run | 作业单 `status` | 先 `approve`（人工令牌不得由模型代签） |
| 4 | 任务卡在 ASSIGNED | 无匹配机器人 | `fleet` 候选为空 | 查电量/能力/区域；补机器人或放宽约束（需评审） |
| 5 | 任务 ABORTED + R1 | 目标在禁入区 | 审计 `RED_LINE_BLOCK` | **不得绕过**；改目标或走人工方案 |
| 6 | 任务 ABORTED + R2 | 超载/危险动作无令牌 | 审计缺 token | 由人签发令牌后重提 |
| 7 | 任务 FAILED + 停机 | 停止区有人（R4） | 审计 `SAFETY_HALT` | 清场 + 人工确认后重跑 |
| 8 | 任务打回 EXECUTING | 证据不全 | `evidence.missing` | 重采证据；连续 3 次打回升级 L3 |
| 9 | 降级到 L4 | 重试与兜底均失败 | RunReport 阶梯 | 挂起 + 通知人；评估遥操 |
| 10 | 技能无法上线 | 版本非 APPROVED | `GET /skills` | 走审批；回滚用 `/skills/{id}/rollback` |
| 11 | 看板空白 | 接口地址错 / CORS | 浏览器 Network | 改数据源；静态托管加 CORS |
| 12 | MCP 客户端 404 | 未连 `/mcp` 或方法名错 | 请求体 | 用 `initialize`/`tools/list` 自检 |
| 13 | A2A 委派 404 | 意图未注册 | 响应 `detail` | 在 `a2a.py` 注册意图映射 |
| 14 | 审计断流 | 写入异常被吞 | `spans_error` | 视为 S1 隐患，立即修复 |
| 15 | 重启后数据没了 | `TIANGONG_DB` 未设置（内存库） | 环境变量 | 设置持久路径并重启 |

## 8. 备份与恢复

### 8.1 备份策略

| 对象 | 方式 | 频率 | 保留 | RPO | RTO |
|---|---|---|---|---|---|
| SQLite 主库 | `VACUUM INTO`（在线、不锁写） | 5 min | 48 h（小时级 7 天） | 5 min | 15 min |
| WAL 文件 | 随主库一并快照 | 5 min | 48 h | 5 min | 15 min |
| episode 分片 | 对象存储版本化 + 跨区复制 | 实时 | 90 天 | 0 | 30 min |
| 技能注册表 | 随主库（skills 表）+ Git 版本 | 5 min | 永久 | 5 min | 15 min |
| 配置（安全区/适配器） | Git（`impl/deploy`） | 每次变更 | 永久 | 0 | 10 min |
| 审计日志 | 追加写 + 冷备 | 日 | 1 年（等保要求 ≥ 6 个月） | 1 天 | 1 h |

### 8.2 在线备份（推荐）

```bash
# 在线热备，不阻塞写入
sqlite3 "$TIANGONG_DB" "VACUUM INTO '/backup/tiangong-$(date +%Y%m%d%H%M).db';"

# 校验
sqlite3 /backup/tiangong-YYYYMMDDHHMM.db "PRAGMA integrity_check;"
```

### 8.3 恢复步骤

```bash
# 1. 停写（服务切只读或摘流量）
kubectl scale deploy/agent-runtime --replicas=0 -n tiangong

# 2. 保存现场（不要直接覆盖）
mv "$TIANGONG_DB" "$TIANGONG_DB.corrupt.$(date +%s)"

# 3. 还原最近可用备份
cp /backup/tiangong-YYYYMMDDHHMM.db "$TIANGONG_DB"
sqlite3 "$TIANGONG_DB" "PRAGMA integrity_check;"   # 必须 ok

# 4. 起服务并验证
kubectl scale deploy/agent-runtime --replicas=2 -n tiangong
curl -s localhost:8000/healthz
curl -s localhost:8000/tg-api/v1/work-orders | python -m json.tool
```

**恢复后必做**：核对最近 24 h 作业单与审计条数；对恢复期间在途作业单**一律重新审批**（不得假定其状态有效）。

### 8.4 备份演练

- 频率：**每季度 1 次**，与应急演练合并
- 判据：从备份还原到可用服务 ≤ 30 min；抽查 3 条历史作业单 trace 可重建
- 记录：演练报告归档（含实际 RTO、发现的问题）

### 9.1 发布窗口

### 9.2 发布流程

```bash
# 1. 门禁（本地/CI 必须全绿）
cd impl && make lint && make test && make coverage && make demo

# 2. 构建镜像并打 tag（语义化版本）

kubectl set image deploy/agent-runtime agent-runtime=registry/tiangong/agent-runtime:1.1.0 -n tiangong
```

### 9.3 回滚

| 对象 | 操作 | 目标时间 |
|---|---|---|
| 服务 | `kubectl rollout undo deploy/agent-runtime -n tiangong` | < 5 min |
| 技能 | `POST /tg-api/v1/skills/{id}/rollback`（body 指定 `to_version`） | 即时 |
| 安全区配置 | Git revert + 重新下发 | < 10 min |
| 数据库 | 还原备份（§8.3） | < 30 min |

### 9.4 变更禁忌

1. **禁止**在生产直接改代码（含热补丁），必须走镜像
2. **禁止**在未备份情况下做数据库结构变更
3. **禁止**跳过安全审查发布技能（技能四态不可绕过）
4. **禁止**为"赶进度"临时关闭红线检查——无此开关，设计上不存在

## 10. 安全运维与审计

### 10.1 账号与权限

| 角色 | 权限 | 说明 |
|---|---|---|
| 操作员 | 下单、查看 | 不可审批、不可急停解除 |
| 安全专员 | 审批、停机、解除隔离 | 令牌签发人 |
| 运维 | 部署、配置、备份 | 不可审批业务单（职责分离） |
| 审计 | 只读全量 | 不可操作 |

**职责分离硬约束**：审批人 ≠ 申请人；运维 ≠ 审批人（等保三权分立要求）。

### 10.2 人工令牌管理

- 令牌只能由人签发（`POST /tg-api/v1/tokens`），模型不得生成、不得复用
- 令牌一次性，绑定作业单与动作类型
- 令牌簿为内存态：**服务重启后旧令牌失效**，需重新签发（这是安全特性，不是缺陷）
- 令牌签发与使用全程进审计（`action=TOKEN_ISSUE` / `TOKEN_USE`）

### 10.3 日志与留存

| 日志 | 内容 | 留存 | 脱敏 |
|---|---|---|---|
| 应用日志 | 请求/异常/降级 | 30 天 | 去除人名、工号 |
| 审计日志 | 审批/急停/回滚/令牌 | ≥ 6 个月（建议 1 年） | 保留操作人（追责需要） |
| 链路 span | trace 全链 | 30 天 | 不含影像 |
| episode | 作业实景数据 | 90 天（受 consent 约束） | 出厂前脱敏 |

### 10.4 合规自查（季度）

- [ ] 红线相关代码变更是否经安全评审
- [ ] 是否存在绕过审批的接口（含内部调试接口）
- [ ] episode 是否 100% 带 `consent_id`
- [ ] 审计日志是否连续无断档
- [ ] 权限矩阵是否与人员在职状态一致（离职即回收）
- [ ] 证书与密钥是否在有效期内

## 11. 容量与性能运维

### 11.1 容量基线（单基地）

| 资源 | 基线 | 扩容触发 |
|---|---|---|
| agent-runtime 副本 | 2 | CPU 持续 > 70% 或 P95 > 1.5 s |
| 机器人并发任务 | 每机器人 1 单 | 队列等待 > 5 min |
| 作业单/日 | 500（基线） | 持续 > 800 |
| DB 增长 | ~20 MB/千单 | 日增 > 500 MB |
| episode 存储 | ~50 MB/千条（含影像） | 使用率 > 75% |

### 11.2 性能调优要点

| 场景 | 手段 |
|---|---|
| 读多写少（看板/查询） | 走读连接 + 多级缓存；缓存 TTL 按数据热度分层 |
| 写入放大 | 批量写、WAL  checkpoint 调优、避免长事务 |
| 安全审查延迟 | 围栏判定为纯内存计算，禁止在其中做 I/O |
| 调度风暴 | 候选打分缓存 + 就绪集增量计算 |
| 事件堆积 | 异步投递 + 批量消费 + 失败重投（不阻塞主链路） |

### 11.3 读写分离注意

- 写走主连接，读走从连接；**写后立即读**可能读到旧值（复制延迟）
- 业务上凡"写后需强一致"的判断（如审批后立即执行），必须走主连接
- 复制延迟监控：`PRAGMA wal_checkpoint` 后比对主从行数

## 12. 演练计划

| 演练 | 频率 | 场景 | 通过判据 |
|---|---|---|---|
| 停机演练 | 月度 | 停止区有人 → R4 | 停机 ≤ 200 ms，任务 FAILED，审计留痕 |
